检查日期：2026-10-16。范围为当前工作区的原生 fnOS 包、配置持久化、前端入口及构建脚本；没有连接 NAS，也没有安装或发布 FPK。

## 安装及启用报错复核（2026-10-16）

### 第二份启用日志与状态管理修复

`micast (1).log` 显示 09:07:37 已执行到管理应用就绪，之后 DLNA 持续响应；09:14:35 又出现新实例，音频流端口从 42404 顺延至 42405。因此最新故障不能继续归为“后端始终没启动”。

本轮移除 `cmd/main` 对 `/proc/<pid>/cwd` 的依赖。该链接在切换用户后可能受进程查看权限限制；状态检测现在通过标准库辅助程序匹配专用用户 UID 与精确的 `python -m micast` 参数，以及对应的 root/runuser 包装进程。它不依赖 PID 文件存在，也能识别旧脚本遗留的主进程。停止时重新扫描这些进程后发送信号，避免继续遗留实例。`status` 返回进程存活状态，就绪检查保留在 `start` 与健康接口中。

新增 9 项进程身份与遗留实例检查；本轮相关检查合计 48 项通过，1 项 Linux shell 测试因平台限制跳过。没有 NAS 实机确认，不能将本地通过视为设备已恢复。

另生成 `dist/fnos/micast-x86-0.3.5-startup-fix.fpk`：基于 09:00 的本地 x86 FPK，仅替换 cmd/main、新增 cmd/service-process.py 并移除宿主字节码；逐文件摘要确认 app.tgz、manifest 及其他原文件内容保持一致。此包通过归档完整性与脚本内容核对，未在飞牛应用中心安装。

- 用户已将同意框 `initValue` 从 `[]` 修正为字符串 `""`，并同步生成器及测试。这项修正正确；已直接检查本地 `dist/fnos/micast-x86-0.3.5.fpk`，安装和升级向导都包含空字符串默认值，源码配置校验通过。
- 提供的 micast.log 反复出现 `Waiting for application startup`，随后有 runuser 的 `Session terminated`；没有应用启动完成记录。历史流请求中的 CancelledError 不能单独视为本次安装失败或启动阻塞的根因。
- `cmd/main` 在启动后立即用持久化 PID 的严格命令行规则判断运行状态，存在 nohup/runuser 尚未完成 exec 时提前失败的竞态。改为启动等待期间只观察本次 `$!` 的存活，状态查询和停止仍采用严格身份校验；启动失败提示区分进程提前退出与就绪超时。
- 原应用日志只进入内存缓冲，未写到被飞牛重定向的 stderr，导致文件只看得到 Uvicorn。fnOS 现在增加一个幂等的控制台 handler，并记录音频 HTTP、经典 AirPlay、可选网络发现、AirPlay 2、DLNA 及管理应用就绪阶段，便于确认是否还有后续阻塞。
- 本地 FPK 还夹带了测试产生的 cmd/__pycache__。构建脚本新增清理，在脚本文本换行规范化之前移除这些宿主版本字节码。
- 本轮 57 项检查通过；新增 Linux shell 竞态回归用例在 Windows 环境跳过。没有完成飞牛实机验证，尚不能认定日志中的全部启动阻塞均已排除。现有 FPK 尚不包含本轮启用修复，需要重建后测试。

## 本轮修正

| 阶段 | 问题与处理 |
|---|---|
| 安装前 | 原向导仅说明自动配置。现完整展示用户协议、隐私政策，默认不勾选同意；`install_init` 和回调都检查当前版本，缺少同意即失败。无需运行应用或访问外部网站即可阅读。 |
| 安装后 | 安装回调的 `PYTHONPATH` 原先遗漏 vendor，现与运行阶段一致；目录、报告、配置及同意记录采用私有权限。协议同意记录仅含版本、时间、来源。 |
| 启动与状态 | 原先只用 `kill -0` 判断 PID 存在。现检查 PID 格式、工作目录和模块命令行，并用 Unix Socket `/health` 判断状态；重复启动遇到存活但不健康的进程会先停止。 |
| 启动失败 | 原先等待超时后直接返回，可能留下进程和 Socket。现走停止清理流程后返回失败。 |
| 停止 | 强制停止前再次检查 PID 身份，避免明显的陈旧 PID 误杀；继续清理仅匹配本应用私有运行时路径的 AirPlay 2 进程。 |
| 升级前 | 备份改为标准库原子写入，权限 0600，包含配置、管理账号、小米账号和凭据、协议同意记录。无配置时移除旧备份。安装及升级均有独立同意页面。 |
| 升级后 | 移除“var 升级必定丢失”的错误假设。备份只补回缺失文件，不覆盖仍存在的新配置；先检查归档成员，只接受约定的普通文件，拒绝链接、路径穿越及重复成员。恢复失败保留备份并返回失败，不再打印警告后继续成功。 |
| 卸载前 | 显式调用停止流程，然后移除 PID 与 Socket，避免只删除标记却未清理运行时。 |
| 卸载后 | 默认策略原先仍保留 access.json 和通知地址密钥。现只保留白名单设备、音频和入口配置，移除小米凭据、管理账号、通知密钥、账号历史和私有运行记录。未知策略采用默认保留配置策略。 |
| 配置变更 | `config_init`、`config_callback` 保持无操作；应用中心未提供独立配置表单，配置由应用内 API 保存及应用，无需重复维护第二套表单。 |
| 打包 | 两份文档、安装及升级向导、应用内正文共用 `web/src/legal-documents.json`；构建前检查生成文件同步，防止用户看到不同版本。保留原有架构、版本一致性、LF 与依赖打包检查。 |

## 数据范围与保留策略

| 操作 | 私有数据 | 共享目录与其他位置 |
|---|---|---|
| 停止／重启 | 保留配置和登录，清理运行标记；正在播放的会话会中断 | 保留日志和导出文件 |
| 升级 | 保留配置与登录；临时升级备份恢复成功后删除 | 保留 |
| 应用内“清空配置与登录” | 删除 micast.json、access.json、xiaomi-account.json、xiaomi-tokens.enc，重新进入引导；不是整个目录擦除 | 不删除日志、导出、备份、浏览器偏好或系统临时文件；界面及隐私政策明确提示 |
| 卸载：仅保留设备配置（默认） | 只保留经白名单筛选的 micast.json | 不自动删除；向导明确提示 |
| 卸载：保留全部私有配置与登录 | 保留上述四个配置与登录文件以及 legal-consent.json；删除私有日志、临时备份和运行标记 | 不自动删除；向导明确提示 |
| 卸载：删除全部私有数据 | 删除应用 var 目录中的内容 | 不自动删除共享目录、用户另存文件、快照或浏览器数据 |
| 重装 | 读取保留配置，不用默认值覆盖协议和端口选择；管理登录已删除时重新引导设置 | 共享目录原有文件仍在 |

保留的设备配置仍包含设备名称、ID 和地址，并非匿名数据。“删除凭据”不代表删除设备信息，也不会撤销小米服务端已经建立的会话。

## 与隐私政策对应的代码事实

- `micast/xiaomi/auth.py`：扫码／导入凭据、令牌交换及续期，账号连接历史独立保留；断开连接删除当前令牌但保留历史。
- `micast/xiaomi/token_store.py`：Fernet 加密，机器特征或自定义环境密钥派生；读取失败存在内置回退值。此设计不能作为对管理员的安全隔离，也不保证跨机器迁移后可解密。本轮如实披露，没有变更密钥体系。
- `micast/access.py`：管理密码使用带盐 scrypt 摘要；Cookie 会话目前有效期三十天。
- `micast/update_checker.py`、设置页：打开设置页会请求 GitHub 发布 API，并使用缓存；飞牛不在应用内下载安装。
- `micast/notify.py`：仅配置 Webhook 时发送登录失效提示；地址可能含密钥，保存于配置。
- `micast/media_cache.py`：DLNA 媒体可进入系统临时文件，正常释放时删除；强杀后残留不由卸载 var 清理覆盖。
- `micast/fnos_storage.py`、`diagnostics.py`：共享日志、诊断及脱敏参考副本；脱敏规则不等于完全匿名，报告仍可包含设备和播放信息。
- `web/src/state.ts`、播放器及动效设置：浏览器 localStorage 保存界面偏好，NAS 卸载无法清除。
- `web/src/components/support-dialog.ts`：本地收款码，无支付订单查询链路；打赏提示与协议同步，邮件须由用户自行发送。

## 飞牛实机验收清单

1. 全新安装：阅读两份正文；未勾选不能安装，勾选后默认配置成功，应用内显示相同版本。
2. x86／ARM 分别启动：应用网关、DLNA HTTP、经典 AirPlay 正常；ARM 隐藏未随包提供的 AirPlay 2，x86 在特权端口不可用时给出可理解的状态。
3. 端口占用：普通自动端口顺延；固定 AirPlay 2 端口冲突只阻断该协议；核心服务失败应阻止安装。
4. 重复启动、异常退出及重启：Socket 重建、状态检查和私有接收进程清理正确；旧 PID 不应影响其他服务。
5. 旧版升级：保留别名、组合、EQ、端口、管理登录与小米凭据；协议同意来源记为升级。坏备份需要明确失败并保留原文件。
6. 三种卸载策略分别实测，检查实际 var 与共享目录内容；尤其验证默认策略没有残留管理密码、通知密钥及小米令牌。
7. 卸载后重装：默认策略需要重新设置管理访问和连接小米，但设备和调音配置仍在；删除私有数据后从空配置开始。
8. 查看共享日志和导出诊断：确认共享权限符合 NAS 管理员预期；按提示可手动删除，浏览器清除网站数据后偏好消失。
