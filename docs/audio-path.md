# 音频怎么走

一次投放分四段：**接收入口 → 每台音箱一路编码 → 音频流服务 → 音箱取流播放**。
多音箱的同步与延迟都发生在第三段，音箱本身不做对齐。

```text
经典 AirPlay / AirPlay 2：发送端 ─▶ 接收入口 ─▶ PCM ─▶ 每台音箱一路编码 ─▶ 音频流服务 ─▶ 音箱取流
DLNA：                    发送端 ─▶ 媒体 URI ─▶ 后台下载到本地缓存 ─▶ 音箱读取局域网短地址
                                                └▶ 需要处理时解码为 PCM ─▶ 同一处理/输出主干
```

## 一、接收入口

| 入口 | 音频从哪来 | 端口 |
| --- | --- | --- |
| 经典 AirPlay | 发送端把 ALAC 音频直接交给 MiCast，MiCast 解码为 PCM | RTSP 默认从 42500 起分配；每个会话再占 3 个 UDP 端口，默认从 42600 起 |
| AirPlay 2 | 飞牛原生包内的 shairport-sync 接收后以 PCM 交给 MiCast | 固定 TCP 7000 |
| DLNA | 收到地址即后台下载；普通 MP3 从本地缓存提供，其余格式及需要 EQ、独立音量或组合的播放使用同一缓存解码进公共管线 | SSDP 发现固定 1900；描述与控制走管理端口 |

- 接收协议设置决定启用哪一类 AirPlay 入口：**自动 / 经典 / AirPlay 2**。经典 AirPlay 与 AirPlay 2 入口可以同时存在，各自独立出现在发送端的投放列表里。
- DLNA 入口与 AirPlay 入口互不影响，可同时开启。
- 局域网里其他 AirPlay / DLNA 播放设备也可以作为输出目标加入（需要开启网络设备发现）。
- AirPlay 2 只在飞牛原生包（单入口，实验性）和 Docker 编排版（多入口）提供；Windows 版与源码运行提供经典 AirPlay 与 DLNA。

## 二、每个入口一条管线

- 每个启用的入口对应一个 PCM 源和一组音频流；多台音箱共享同一个 PCM 源，各自编码，互不等待。
- 每台音箱可能拿到的是同一个流，也可能是为它单独生成的流：左右声道各一路、单独 EQ 一路。仅当确实有音箱需要未拆分的原始混音时，才会额外生成一路。
- 组合的播放模式与声道决定拆不拆：同声播放时成员共用同一路；立体声时左右各一路，某台选「双」则回到共用那路。
- 单台音箱的 EQ、夜间模式、响度补偿如果与其他人不同，那台音箱自己一路；曲线相同的音箱共用一路。
- 给音箱的地址里带着入口与音箱标识，所以同一个音箱在不同组合里可以拿到不同的流。

## 三、编码

- 可以输出的格式：MP3、FLAC、WAV；码率 128k / 192k / 320k；采样率 44.1 / 48 kHz。
- 打开转码（默认）时按所选格式实时编码，实时输出所需带宽约：MP3 320k 约 0.32 Mbit/s，FLAC 约 0.7–1.1 Mbit/s（随内容变化）。
- 关闭转码时输出 PCM 直通：不重新编码，直接把 PCM 套上音频流头送出，带宽约 1.5 Mbit/s（48 kHz 立体声）。
- 如果这台音箱带 EQ、夜间模式、响度补偿或声道拆分，它仍会走一次编码（这些处理需要重编码）。
- 编码在应用进程内完成，不需要额外安装 ffmpeg。
- 改动格式、码率或采样率后，正在播放的音箱会用新地址重新取流，不需要重连发送端。AirPlay 的 EQ 改动只重建编码阶段；DLNA 从当前媒体位置重建处理，可能有短暂间隙。

## 四、音频流服务

- 默认监听 42400；管理页面默认 42300，两者可以分别修改。音箱通过 HTTP 拉流。
- 每路流一个地址；地址里带入口、音箱与一次性参数，防止音箱复用旧内容。
- 首段音频会被缓存并补给后来加入的音箱，让中途加入不从头开始；MP3 除外（MP3 自带同步标记，重放旧内容反而会错位）。
- 同一台音箱重新取流时按新地址连接，旧连接自动释放。

## 五、每台音箱的延迟线

每台取流的音箱在 MiCast 侧有一条独立的缓冲（延迟线），默认保留 0.25 秒音频作为安全余量，用于吸收发送端与网络的抖动。

- **组合内的对齐**：组合成员各有一个相对偏移，MiCast 取其中**最小**的一台作为“实时边”（不额外保留），其余按差值往后垫。也就是说：改动某一台的偏移时，被垫住的通常是相对更快的那一台。
- **偏移变大**：需要先攒够差值的音频。这段时间这台音箱收不到真实音频，MiCast 会按它自己的格式喂静音帧（MP3、FLAC、PCM/WAV 各有一种），所以听感是“这台先安静一下，然后按新偏移恢复”，连接不会中断。攒够所需的时长约等于增加的毫秒数。
- **偏移变小**：立即生效——丢掉缓冲里最老的一段（整块丢弃，不切断音频帧），这台音箱马上提前。
- **来源短暂断供**：发送端或编码出现约 0.15 秒以上的空档时，MiCast 从延迟线里取一段补上，避免空档直接传到耳朵里。
- **落后太多**：某台音箱比实时边落后超过 4 秒（可调）时，它会被跳回实时位置，而不是无限堆积。
- 延迟改动不重启编码器、不重连发送端；暂停、恢复和停止会清空或重建这条缓冲。

## 六、让音箱开始播放

- 播放开始时，MiCast 通过小米云端把音频流地址发给目标音箱，音箱自己去取流。每台音箱一个地址，彼此独立。
- 组合播放时所有成员同时收到指令，时间差由延迟线处理，不靠错开发指令来对齐。
- 发送端点击暂停/继续/停止时，音箱随之暂停/继续/停止；会话结束后约 3 秒内释放音箱。
- 某台音箱没接住指令（离线、云端超时）时，MiCast 会记录并按间隔重试，最多 5 次；界面上能看到是哪一台失败。
- 音箱接了指令却始终不取流（多数是不支持当前格式）时，MiCast 会停掉它，避免空转。
- 组合的基准音箱离线时，整个组合暂停并等待它回来，而不是让其他成员越播越偏。
- 音箱被语音助手或闹钟打断后，MiCast 会检测到并自动恢复原来的投放。

## 七、格式兼容性

MiCast 记录每台音箱对 MP3、FLAC、WAV、PCM 的实测结果（不依赖型号猜测），结论有三个来源：

- **播放时自动确认**：正在播放的格式，如果音箱持续取流，就记为支持。
- **空闲时自动检测**：没有播放时，逐台、依次用静音的测试流检测其余格式，不影响听感；一次只测一台，有播放开始立即让位。
- **诊断页手动检测**：会播放一小段测试音，逐项测四种格式，结束后恢复原来的播放。

两点例外说明：

- **PCM（直通）不能用取流来证明**。有的型号会照常全速取流却不出声，所以 PCM 的结论不由自动检测给出，界面显示为“需试听”，以实际听感为准；已知不出声的型号直接标为不支持。
- 结论会自动重测：超过约 24 小时的结论会被重新检测；超过 30 天的结论不再参与组合的格式推荐，只作为历史记录显示。

## 八、异常恢复

- MiCast 每 2 秒检查一次每个入口的链路信号：会话是否活跃、音源是否在出数据、音箱是否在取流、编码是否正常。
- 出现异常时按阶梯处理：先只重建受影响的管线，其次重启该入口的音源，再重发播放指令，再踢掉卡住的音箱连接；连续多次仍未恢复才会标记为不健康并放慢重试。
- 处理范围只到出问题的那个入口，其他入口继续播放。
- 同一入口的恢复经过公共仲裁；暂停或被接管后，正在等待的旧恢复取消，不能抢回目标。
- 切换接收协议、接收器模式或开关 AirPlay 2 属于服务级变化，会造成短暂中断。

## 九、共同控制与协议差异

三种入口共享会话、目标租约、DSP、HTTP 延迟线和控制状态。网络 AirPlay 输出在推送前完成声道/EQ/增益处理，并显式把 48 kHz 输入重采样到 44.1 kHz。

DLNA 是有限媒体，可以保存暂停位置并定位；实时 AirPlay 来源只暂停 MiCast 输出，不承诺控制手机播放进度。媒体结束后保留覆盖组合延迟的尾部排空时间，再释放资源。

DLNA 接收统一通过本地下载缓存提供媒体。收到 SetAVTransportURI 后开始后台下载，Play 立即响应并报告 TRANSITIONING，下载和输出准备完成后变为 PLAYING。普通单音箱 MP3 且使用联动音量时提供支持 HEAD / Range / Content-Length 的本地文件地址；独立音量、EQ、声道、响度、组合或其他格式通过已有音频管线处理同一个文件。拖进度及暂停恢复复用缓存文件，不再次访问远端。取消或换歌会撤销旧短地址；下载失败会报告错误，不向音箱下发原始远端地址。命令接受、下载就绪和真实出声是不同阶段。

下载使用异步 HTTP 和有界 DNS 解析，不占用解码线程进行远端网络读取。拒绝请求时可重试另一种 HTTP 客户端指纹；超时不会切换投递路径。缓存使用临时文件，单曲上限 200 MiB、全局上限 512 MiB、最多 16 个入口、同时最多 4 个下载；停止、换歌及关闭服务会取消任务并释放文件。完整文件准备后才解码或提供音频，超大文件和持续无结束的媒体会明确失败。

设计参考：[miair-next 的预下载与本地代理](https://github.com/deerwan/miair-next/blob/d052ff5e2cfa3f3f6383ac92d4d2a709d4a128bb/backend/app/engine/dlna/device_server.py)。MiCast 使用自己的有界磁盘缓存，并继续使用现有的音频管线和会话代次管理。

### 小米云端连不上时

- 所有对外请求都有超时与并发上限，域名解析有独立的解析通道与缓存，所以一个不响应的外部服务不会拖住界面或其他功能。
- 云端连续无响应时，界面显示账号"云端暂时没有响应"，诊断页给出红字提示；后台的格式检测、音箱状态轮询与播放重试在此期间暂停，避免继续加重故障。
- 登录凭证不会被删除，也不会被判定为失效。网络恢复后（音箱列表每 30 秒轮询一次）自动回到已连接，不需要重新登录或重启应用。
- 运行记录里每次故障只记一条：开始时的原因与恢复的时刻。

## 十、在哪里看

| 位置 | 看什么 |
| --- | --- |
| 诊断 → 链路 | 音源、转码、流、音箱四段是否正常，卡在哪一段，最近事件 |
| 诊断 → 连接明细 | 每路流的取流台数、已发送字节、编码耗时、客户端缓冲与延迟、链路丢弃、CPU 与事件循环延迟 |
| 诊断 → 播放诊断 | 播放测试音频、检测格式、重建管线 |
| 诊断 → 运行记录 | 运行日志（可按来源、级别、时间范围筛选）、复制日志、导出诊断报告 |
| 链路页 | 每个入口的播放目标、组合成员、延迟与声道 |
| 音箱页 | 每台音箱的在线状态、音量、EQ、格式兼容性 |


### 带屏小爱的歌曲显示

经典 AirPlay 和随包部署的 AirPlay 2 接收歌曲元数据后，使用小米曲库匹配的
`audioID` 重新下发当前音频流。AirPlay 2 使用每个接收进程独立的非阻塞元数据
FIFO，不从 PCM 通道解析封面。远程 TCP PCM 服务仍需要另行提供元数据，单靠
PCM 字节无法还原歌名与歌词。

DLNA 使用控制器的 DIDL 歌名、歌手（兼容 creator）在下发播放前匹配曲库，原始
缓存文件与 DSP 输出共用相同歌曲标识。查询最多等待 5 秒，失败继续播放；切歌
清除旧标识，暂停、定位和恢复播放保留当前曲目标识。该路径不额外重播歌曲来
更新屏幕。

屏幕上的封面、歌名与歌词由音箱固件根据小米曲库 audioID 获取；MiCast 没有将
任意 LRC 文件或网页滚动歌词写入音箱的通用接口。匹配成功不等于有歌词，仍取决
于曲库内容、权限和机型固件；本地流定位后的歌词时间轴是否同步需真机验证。
